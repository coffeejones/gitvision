# PR Comment Format v1 — spec

_Captured 2026-05-11. This is the agreed format for RepoBaron's GitHub
App PR comment. All future signal-development, MCP-tool work, and
repobaron.com deep-dive design references this as the contract: "what
does the reviewer actually see, and what does each section commit us to
producing?"_

## Design principles

1. **The reviewer is the decision-maker, not the bot.** Our comment helps
   them understand the PR faster — it does NOT replace their judgment.
   Section names reflect this: "Suggested verification" not "Required
   before merge".

2. **Every claim cites deterministic evidence.** Complexity values, file
   paths, function names, caller counts — all computed by our pipeline,
   not generated by an LLM. The footer makes this explicit as a
   trust-anchor: *"No LLM in this comment."*

3. **The comment is a summary; repobaron.com is the deep-dive.** PR comments
   are bounded at ~25 lines. Detail, history, narrative, cross-PR context
   lives on the workspace.

4. **Author-narrative + RepoBaron-analysis, not RepoBaron-narrative.**
   The "what this PR does" section quotes the PR author's own description,
   then layers our metrics underneath. We don't paraphrase what the human
   wrote.

5. **Four reviewer questions answered, in order:**
   1. What is this PR about? → **What this PR does**
   2. Where are the changes? → **Where the changes are**
   3. What should I be aware of? → **What to watch for**
   4. What should I check before approving? → **Suggested verification**

## The format (rendered example)

```markdown
## RepoBaron Review

### What this PR does
> _"Add duplicate-name validation for pet creation"_
> — from PR description by `@coffeejones`

RepoBaron analyzed: **3 functions** modified across **2 files**, net
complexity **+7**, **1 new branch**, **0 tests** added.

### Where the changes are
| File | Functions modified | Net complexity Δ |
|---|---|---|
| `Owner.java` | `addVisit`, `getPet` | **+5** |
| `PetController.java` | `processCreationForm` | **+2** |
| `OwnerService.java` | `validatePet` | 0 _(refactor only)_ |

### What to watch for
| Signal | Detail |
|---|---|
| 🔴 **Complexity delta** | `Owner.addVisit` rose from 6 → 11 — new branch handles the duplicate-name detection |
| 🟡 **Blast radius** | 7 callers depend on changed functions; 3 are cross-module (`audit/`, `service/`) |
| 🟡 **Untested change zone** | `processCreationForm` is on top-5 untested hotspots and now has 1 new branch |
| 🟢 **No duplicates flagged** | Change does not appear to duplicate existing utilities |

### Suggested verification
1. Add unit test for the new branch in `Owner.addVisit` covering `petsByName.get(...)` null path
2. Verify `PetController.processCreationForm`'s 4 callers still pass `BindingResult` correctly
3. Spot-check `AuditLogger` (cross-module dependency) — no test will catch a regression there

---
[Full analysis ↗](https://repobaron.com/...) · _Signals computed deterministically — no LLM in this comment_ · [Configure thresholds](https://repobaron.com/docs/config)
```

## Section-by-section data requirements

### "What this PR does"

| Field | Source | Status |
|---|---|---|
| PR title (first line of quote) | GitHub API (`pull_request.title`) | ✅ trivial when GitHub App built |
| Author narrative (rest of quote) | GitHub API (`pull_request.body` first ~80 chars) | ✅ trivial when GitHub App built |
| Author handle | GitHub API (`pull_request.user.login`) | ✅ trivial when GitHub App built |
| Functions modified count | Diff-aware AST analysis | ❌ **GAP** — see below |
| Files modified count | Diff-aware analysis (or git diff stat) | 🟡 git diff is trivial; AST-level is not |
| Net complexity Δ | Before/after complexity computation | ❌ **GAP** — see below |
| New branches count | AST-level diff of cyclomatic structure | ❌ **GAP** — see below |
| Tests added count | Diff-aware test-file detection | 🟡 detect by file path pattern is easy; semantically-test-additions is harder |

### "Where the changes are"

| Field | Source | Status |
|---|---|---|
| File path | Git diff | ✅ trivial |
| Functions modified (per file) | Diff-aware AST analysis | ❌ **GAP** |
| Net complexity Δ per file | Diff-aware AST analysis | ❌ **GAP** |
| "Refactor only" label | Heuristic: complexity unchanged + function count unchanged | 🟡 derived once GAP closed |

### "What to watch for"

| Signal | Source | Status |
|---|---|---|
| Complexity delta (per function) | Diff-aware AST analysis | ❌ **GAP** |
| Blast radius (caller count + list) | `blast_radius` MCP tool | ✅ **WORKS** (P6 5/5 strong in eval) |
| Cross-module flag | Post-process blast_radius callers vs file-path module heuristic | 🟡 small extension on existing data |
| Untested change zone | `untested_hotspots` MCP tool | ✅ **WORKS** (P2 5/5 strong in eval) |
| "Now has new branch" qualifier | Diff-aware AST analysis | ❌ **GAP** |
| Duplicate utility flagged | `find_duplicates` MCP tool | 🟡 **PARTIAL** — current impl is structural (regex/AST shape), needs semantic for AI-aware claim |

### "Suggested verification"

This is the section that needs the most design work. Recommendations
must be:
- Specific to the change (not generic)
- Grounded in observed signals (cite which signal triggered each)
- Actionable in under 30 minutes per item
- Capped at 3 items (more = ignored)

**Status:** ❌ **GAP** — needs a rules engine that maps signal patterns
to recommendation templates. Examples:
- `complexity_delta > 5 AND coverage_delta == 0` → "Add unit test for the new branch covering [the new conditional]"
- `cross_module_callers > 0 AND tests_added_in_that_module == 0` → "Spot-check [module] — no test will catch a regression there"
- `signature_changed AND caller_count > 0` → "Verify [N] callers still pass [arg] correctly"

## The big gap: diff-aware analysis

Format B v2 reveals that **the single biggest infrastructure missing is
diff-aware AST analysis**. Today RepoBaron's pipeline works on whole-
snapshot basis (analyze a repo, get its current state). For PRs we need:

- Compare base snapshot (target branch) vs head snapshot (PR branch)
- Identify which functions changed
- Compute before/after complexity per function
- Detect new branches (cyclomatic structure changes)
- Surface signals that fire SPECIFICALLY on the diff, not on the whole repo

This is a real piece of infrastructure work — probably 2-3 weeks. It
unblocks 60% of Format B v2's claims.

`compare_sessions` MCP tool already exists for snapshot diffs but
returns summary-level deltas, not function-level. Either extend it or
build a new `analyze_diff(base_session, head_session)` tool.

## Open question: LLM-summary opt-in

The "What this PR does" section uses the **author's own description**.
This respects "no LLM in this comment". Two failure modes:

1. PR author writes "fix" as the entire description → we have no narrative
2. PR author writes 5 paragraphs → we truncate aggressively

**Option X (default):** Use author description verbatim, truncate to
80-120 chars. If empty, skip the quote block entirely and show only
metric summary.

**Option Y (opt-in via `gitvision: smart-summary` config):** LLM-generate
a 1-sentence what-this-does from the diff. Mark explicitly in footer:
*"Summary AI-generated (verify) — all signal claims are deterministic."*

**Recommendation:** Ship X. Add Y as opt-in feature in v1.5. Many teams
will prefer X because they already have PR template enforcement.

## Trust principles & configuration

**Deterministic claim.** Every signal in the "What to watch for" table
must be computed by the pipeline, not generated. If a team wants LLM
opinions, they get them on repobaron.com deep-dive (where users
expect AI), not in the PR comment (where they want facts).

**Suppress mechanism.** Three levels:
1. Per-comment: reviewer reacts with 👎 — telemetry feedback, not config change
2. Per-repo: `gitvision: ignore complexity-delta` in `.gitvision.yml`
3. Per-team: workspace settings on repobaron.com

**Threshold configuration.** All severity tiers (🔴/🟡/🟢) come from
configurable thresholds with sensible defaults:
- Complexity delta: 🟢 0-2, 🟡 3-7, 🔴 8+
- Blast radius: 🟢 0-3 callers, 🟡 4-15, 🔴 16+
- Coverage delta: 🟢 +1 test/function, 🟡 0 with low pre-existing coverage, 🔴 0 with new branch in untested function

## Edge cases & failure modes

| Scenario | Behavior |
|---|---|
| PR with 0 signals firing | Show "RepoBaron Review: nothing notable on this PR ✅" — short comment, no false alarms |
| Repo with no test directory detected | Skip the test-coverage column in "Where the changes are"; flag in footer that test detection is uncertain |
| Function modified but unable to AST-parse (e.g. malformed code) | Skip it from the table, note in footer "RepoBaron could not analyze N functions" |
| Very large PR (50+ files) | Show top 5 by complexity-delta in table; link to deep-dive for the rest |
| Force-push / amended PRs | Re-analyze; replace previous comment (not append a new one) |
| Bot-authored PR (Dependabot, Renovate) | Skip the author-quote section (bots don't write narratives); show only metric summary |

## What's "in" for v1 vs "later"

**In for v1 (must work day 1 of PR-bot launch):**
- "Where the changes are" table (file-level, derived from git diff)
- "What to watch for": Blast radius signal ✅, Untested change zone ✅
- "What this PR does" with author narrative (no LLM, Option X)
- Footer with trust-anchor + config link

**Soft-in for v1 (works but with caveats):**
- Complexity delta (need diff-aware infra — could ship without if blocker)
- Cross-module flag (small post-processing)
- "Suggested verification" with 2-3 rule-based templates

**Later (post-v1):**
- Semantic duplicate detection (the AI-aware claim)
- LLM-summary opt-in (Option Y)
- Per-team configuration UI on repobaron.com
- Customizable verification rule packs
- Cross-PR trend mentions ("3rd risky change to this file this month")

## Roadmap consequences

Picking Format B v2 means our next 3 infra investments are:

1. **Diff-aware AST analysis** (2-3 weeks) — unblocks complexity-delta,
   function-modification detection, new-branch detection
2. **GitHub App skeleton + webhook listener** (1-2 weeks) — gets the
   author narrative + diff into our pipeline
3. **Rules engine for "Suggested verification"** (1-2 weeks) — maps
   signal patterns to verification recommendations

Total: ~5-7 weeks from "we have the spec" to "we ship v1 of the bot".
Realistic for a hobby developer with other commitments — possibly
3-4 months of calendar time. Matches the v1 timeline in
`scope-and-sequence-2026-05.md`.
